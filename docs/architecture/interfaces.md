# MVP Interface Contracts

Status: Approved design baseline
Date: 2026-07-14

This document is the contract source for backend models and frontend types. Python/Pydantic definitions are authoritative at runtime; frontend TypeScript types must stay structurally equivalent through tests or generated schema once that is introduced.

## Conventions

- API prefix: `/api/v1`.
- JSON field names: `snake_case` on the wire in the MVP.
- IDs: UUID strings generated by the backend.
- Times: UTC RFC 3339 strings, for example `2026-07-14T03:20:00Z`.
- Durations: integer milliseconds.
- Rows: JSON-compatible scalar values only; decimal/date/time values are serialized deterministically by the backend.
- Optional values are explicit JSON `null`, not omitted, unless the endpoint documents otherwise.
- Public errors never contain credentials, connection URLs, stack traces, or unrestricted database messages.

## API draft

### `GET /health`

Returns process health only. It must not expose database credentials or perform an expensive Agent run.

```json
{ "status": "ok" }
```

### `POST /api/v1/analyses`

Creates an in-process task.

Request: `AnalysisRequest`
Response: `202 Accepted` with `AnalysisTaskStatus` in `queued` state.
Errors: `422` validation, `429` local capacity/budget protection, `500` task creation failure.

### `GET /api/v1/analyses/{task_id}`

Returns the latest `AnalysisTaskStatus`. The frontend polls while state is `queued` or `running` and stops on `succeeded`, `failed`, or `needs_input`.

Errors: `404` when the task is unknown or was lost/expired after process restart.

### No MVP cancellation endpoint

Cancellation, task listing, history, retry-from-UI, and deletion are deferred because process-local tasks are short-lived and single-user. Server timeouts still bound work.

## Pydantic model drafts

The syntax below is intentionally close to Python 3.12/Pydantic v2 but is a contract draft, not current executable code.

```python
from datetime import datetime
from enum import StrEnum
from typing import Any, Literal
from uuid import UUID

from pydantic import BaseModel, Field

JsonScalar = str | int | float | bool | None


class AnalysisRequest(BaseModel):
    question: str = Field(min_length=1, max_length=2_000)


class TaskState(StrEnum):
    QUEUED = "queued"
    RUNNING = "running"
    SUCCEEDED = "succeeded"
    FAILED = "failed"
    NEEDS_INPUT = "needs_input"


class StepType(StrEnum):
    TASK = "task"
    AGENT = "agent"
    TOOL = "tool"
    SQL = "sql"
    REPORT = "report"


class StepStatus(StrEnum):
    STARTED = "started"
    SUCCEEDED = "succeeded"
    FAILED = "failed"


class AgentExecutionStep(BaseModel):
    sequence: int = Field(ge=1)
    type: StepType
    name: str
    status: StepStatus
    message: str
    attempt: int | None = Field(default=None, ge=1, le=3)
    started_at: datetime
    finished_at: datetime | None = None
    duration_ms: int | None = Field(default=None, ge=0)


class SqlErrorCode(StrEnum):
    PARSE_ERROR = "parse_error"
    UNSAFE_SQL = "unsafe_sql"
    UNKNOWN_TABLE = "unknown_table"
    UNKNOWN_COLUMN = "unknown_column"
    SYNTAX_ERROR = "syntax_error"
    TYPE_ERROR = "type_error"
    PERMISSION_DENIED = "permission_denied"
    TIMEOUT = "timeout"
    CONNECTION_ERROR = "connection_error"
    RESOURCE_LIMIT = "resource_limit"
    EXECUTION_ERROR = "execution_error"


class SqlError(BaseModel):
    code: SqlErrorCode
    message: str
    retryable: bool
    failed_sql: str
    attempt: int = Field(ge=1, le=3)
    database_code: str | None = None
    hint: str | None = None


class SqlExecutionResult(BaseModel):
    ok: Literal[True]
    sql: str
    columns: list[str]
    rows: list[dict[str, JsonScalar]]
    row_count: int = Field(ge=0)
    truncated: bool
    duration_ms: int = Field(ge=0)
    attempt: int = Field(ge=1, le=3)


class TableData(BaseModel):
    columns: list[str]
    rows: list[dict[str, JsonScalar]]
    row_count: int = Field(ge=0)
    truncated: bool


class ChartSpec(BaseModel):
    type: Literal["line", "bar", "pie"]
    title: str
    x_field: str
    y_field: str
    series_field: str | None = None


class AnalysisReport(BaseModel):
    title: str
    summary: list[str] = Field(min_length=1, max_length=8)
    sql: str
    table: TableData
    chart: ChartSpec | None
    assumptions: list[str] = []
    warnings: list[str] = []


class PublicTaskError(BaseModel):
    code: str
    message: str
    retryable: bool = False


class AnalysisTaskStatus(BaseModel):
    task_id: UUID
    state: TaskState
    question: str
    steps: list[AgentExecutionStep]
    report: AnalysisReport | None = None
    error: PublicTaskError | None = None
    created_at: datetime
    updated_at: datetime
    completed_at: datetime | None = None
```

Implementation note: use `Field(default_factory=list)` instead of mutable list defaults in executable Pydantic code. Defaults are shortened above for readability.

## Model purpose and invariants

### `AnalysisRequest`

Carries only user intent. The client cannot set SQL, retry count, row cap, timeout, model, database, or allowlists. Whitespace-only questions must be rejected by an additional validator.

### `AnalysisTaskStatus`

Is both the `POST` acknowledgment and polling response. Invariants:

- `report` is non-null only when `state == "succeeded"`.
- `error` is non-null only for `failed` or `needs_input`.
- `completed_at` is non-null only for terminal states.
- Step sequence values are strictly increasing and stable across polls.

### `SqlExecutionResult`

Represents successful execution only. A failed `execute_sql` call returns `SqlError` in the discriminated tool envelope below. `row_count` is the number returned after the server cap; `truncated` states whether additional rows may exist.

### `SqlError`

Carries a sanitized, model-actionable failure. `retryable` is assigned by deterministic backend classification, never by the model. `failed_sql` is retained for repair/audit but is not shown when it contains values classified as sensitive by future policy.

### `AnalysisReport`

Is the Agent's structured final output and the frontend's rendering input. Conclusions must be supported by `table.rows`; the backend validates structure, while analytical grounding is covered by prompt rules and tests.

### `ChartSpec`

Describes data mapping, not an ECharts option blob. The frontend converts it through trusted local code. `chart` is nullable because forcing a chart for unsuitable or empty results creates misleading output. This is the deliberate adjustment from the minimum example, which always included a chart object.

### `AgentExecutionStep`

Provides safe user-visible progress. It records phase/status/timing but excludes chain-of-thought, raw prompts, credentials, unrestricted database errors, and full result payloads.

## Agent tool contracts

All tools return JSON-serializable typed envelopes. Tool implementations may raise only unexpected programming/infrastructure exceptions to the coordinator; expected validation and database outcomes are values.

### `list_tables`

Input:

```json
{}
```

Success output:

```json
{
  "ok": true,
  "tables": [
    { "schema": "analytics", "name": "sales", "comment": "Desensitized sales facts" }
  ]
}
```

The backend applies schema/table allowlists before returning metadata.

### `get_table_schema`

Input:

```json
{ "table_name": "sales" }
```

Success output:

```json
{
  "ok": true,
  "schema": "analytics",
  "table": "sales",
  "columns": [
    {
      "name": "sale_date",
      "data_type": "date",
      "nullable": false,
      "comment": "Order date"
    }
  ]
}
```

Failure output uses a small metadata error envelope, for example `{ "ok": false, "code": "table_not_allowed", "message": "Table is unavailable" }`, without revealing hidden table names.

### `execute_sql`

Input:

```json
{ "sql": "SELECT sale_date, SUM(amount) AS revenue FROM sales GROUP BY sale_date" }
```

Success output is `SqlExecutionResult` with `ok: true`.

Expected failure output:

```json
{
  "ok": false,
  "error": {
    "code": "unknown_column",
    "message": "The query references an unknown column",
    "retryable": true,
    "failed_sql": "SELECT sales_day FROM sales",
    "attempt": 1,
    "database_code": "1054",
    "hint": "Refresh the schema for sales before repairing the query"
  }
}
```

The tool does not accept client-controlled timeout, row limit, connection, schema allowlist, or attempt. The coordinator injects attempt context and server policy.

### No `build_report` tool

The Agent runner is configured with `AnalysisReport` as its final structured output. See `overview.md` for the decision rationale.

## Report JSON example

```json
{
  "title": "近三个月品牌销售额趋势",
  "summary": [
    "品牌 A 销售额连续三个月下降。",
    "品牌 A 的降幅在所查询品牌中最大。"
  ],
  "sql": "SELECT month, brand, SUM(amount) AS revenue FROM sales WHERE month >= '2026-04-01' GROUP BY month, brand ORDER BY month, brand LIMIT 1000",
  "table": {
    "columns": ["month", "brand", "revenue"],
    "rows": [
      { "month": "2026-04", "brand": "品牌 A", "revenue": 125000.0 }
    ],
    "row_count": 1,
    "truncated": false
  },
  "chart": {
    "type": "line",
    "title": "各品牌月度销售额",
    "x_field": "month",
    "y_field": "revenue",
    "series_field": "brand"
  },
  "assumptions": ["销售额使用 amount 字段汇总。"],
  "warnings": []
}
```

Changes from the requested minimum example:

- Adds `row_count` and `truncated` so consumers know whether the table is complete.
- Makes `chart` nullable instead of fabricating unsuitable visualizations.
- Adds `assumptions` and `warnings` to expose business interpretation and execution limitations.
- Keeps chart fields declarative and narrow; frontend-owned code creates ECharts options.

## Error protocol

HTTP errors describe transport/request failures. Task errors describe asynchronous analysis outcomes.

HTTP error shape:

```json
{
  "detail": {
    "code": "invalid_request",
    "message": "Question must not be blank"
  }
}
```

Terminal task examples:

- `needs_input` + `ambiguous_metric`: user clarification can resolve the issue.
- `failed` + `unsafe_sql`: policy denied execution; no repair retry.
- `failed` + `query_timeout`: execution exceeded the server budget.
- `failed` + `retry_exhausted`: three SQL attempts failed (initial + two repairs).
- `failed` + `provider_error`: model/provider run failed.

The API does not return `SqlError` as an HTTP failure for a running task; it records a safe step and lets the bounded coordinator decide retry or terminal status.

## Frontend polling contract

- Poll only `queued` and `running` tasks.
- Use a default interval selected during frontend implementation; do not poll faster than the server's documented minimum.
- Stop immediately on a terminal state.
- Treat `404` as task loss/expiry and offer a new submission, not an automatic duplicate run.
- Do not infer progress percentage from step count; the workflow is not fixed-length.
- Never render `message`, SQL, or summary as HTML.

## Compatibility rule

Contract changes that rename/remove fields or alter semantics require updates to backend tests, frontend types/tests, examples here, and the handoff. Additive optional fields may be introduced without an ADR; changes to task lifecycle, execution model, or security semantics require an ADR.
